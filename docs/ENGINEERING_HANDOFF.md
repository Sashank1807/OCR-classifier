## 4. Current problems: generalization risk — is this tuned for unseen documents, or overfit to the benchmark set?

The user directly asked, mid-session: *"are you improving the OCR pipeline for unseen images, or just improving for the example images and hardcoding — is this dynamic for unseen images?"* This section records that question and the honest answer, so the next session doesn't lose it. **No code was changed in response to this question** — it's an open problem, not yet acted on.

### The honest answer: it's a mix, and the risk is real but specific

**What is NOT the problem** — no filename-specific or document-specific special cases were added anywhere (no `if filename == "1000517666.jpg"`, no per-document branches). Where the *original* code had that exact anti-pattern — hardcoded company names (`"hetero"`/`"derma"`/`"glow"`) for banner detection, an absolute pixel coordinate (`x0 > 1260`) tuned to one capture resolution, packing values fabricated by regex-matching product description text — it was removed this session, not added. Every fix changes a general *mechanism* (evidence-gated column insertion, similarity-based row merging, arithmetic-conflict-triggers-reocr, real bbox-geometry candidate scoring, header-keyword column-role mapping), not a rule about specific example documents.

**What IS the problem** — those general mechanisms all have **threshold constants**, and several of them were chosen or validated by running the real pipeline against the ~11 ground-truth documents and checking what broke:

| Constant | Current value | How it was chosen |
|---|---|---|
| Side-panel x-cutoff (`_detect_table_bounds`) | `x0 > w * 0.78` | Reverse-engineered from exact token pixel-positions on **one** real document (`1000517666.jpg`) — see section 3.6 |
| RapidOCR `det_box_thresh` / `det_unclip_ratio` / `text_score` | `0.35` / `2.0` / `0.35` | Taken from the implementation plan's suggested starting values; only empirically checked against the same ~6-7 core documents |
| Column-insertion corroboration | ruling line OR ≥3 data lines, gap width ≥30px | Chosen to keep one synthetic unit test passing (`test_global_column_model_infers_missing_numeric_columns`, 3 rows) — never checked against a document with, say, 15 rows where the right count might need to be higher |
| Row-merge similarity | length-ratio ≥0.7 AND `SequenceMatcher` ≥0.85 AND matching trailing-digit-run | Chosen specifically to separate the audit's named examples (`PARA500`/`PARA500XR`, `MINOSTRONG 1.25`/`2.5`) — works for trailing-digit dosage variants, would NOT catch a pure-alphabetic-suffix variant (e.g. `"PARACETAMOL"` vs `"PARACETAMOLXR"`, no digits involved) — documented as a known residual gap when the fix was written |
| Resolution-normalization target | reverted to original `min_dim<650→2x` | Tried 1400px and 900px targets, both measurably broke real documents differently; reverted rather than keep guessing a third number |

This is a real instance of the classic "tuned on the validation set" problem: passing the benchmark is necessary but not sufficient evidence these numbers hold up on a genuinely new document with a different resolution, printer, or table layout that wasn't part of this tuning loop.

**A concrete example of catching this and backing off rather than compounding it**: resolution normalization. Rather than keep adjusting the target-dimension constant until benchmark numbers looked acceptable, it was reverted to the original, previously-validated fixed rule, and the code comment in `preprocessor.py` states plainly that the underlying problem (small text in the 700-900px band) remains unsolved. This was a deliberate choice not to ship a third guessed constant.

### Solution directions discussed with the user (not yet implemented — needs a scoping decision before any code changes)

**A. Fix the validation methodology (data problem, not a code problem)**
- Grow the ground-truth set with documents that deliberately vary resolution, printer type, table layout, and capture conditions — even 15-20 more diverse documents would meaningfully de-risk this.
- Split into a **dev set** (used to choose constants) and a **held-out test set** (checked only once, at the end, never used to pick a threshold). Right now everything is effectively "dev" — the same documents are used both to tune and to declare success, which is precisely how this class of overfitting happens.
- Cheaper interim option: synthetically perturb the existing good documents (resize, rotate, blur, crop differently) to create more "unseen-like" variants without collecting new real photos, and check whether current thresholds (especially the 0.78 side-panel ratio and the RapidOCR detector settings) survive those perturbations.

**B. Replace fixed global constants with document-relative/adaptive computation where feasible (architecture problem)**
- **Side-panel boundary**: derive the cutoff from the table's own detected header row (e.g. rightmost real column token + margin) instead of a fixed fraction of image width, so it's anchored to what's actually on the page rather than an assumed universal ratio.
- **Resolution normalization**: retry-based instead of single-target — attempt at native resolution first, check whether detection looks sparse (missing expected header keywords, numeric fill ratio far below typical), and only escalate to progressively higher upscaling if the first pass looks incomplete.
- **RapidOCR detector settings**: two-pass strategy — conservative/high-confidence settings first, fall back to the more sensitive (and more merge-error-prone, per section 3.4's `unclip_ratio` finding) settings only for cells/regions that come back empty or sparse, rather than always running the permissive settings globally.
- **Column-insertion gating** is actually a good example of this pattern already applied (requires convergent evidence — ruling line OR multi-line corroboration — rather than one lone threshold); the same pattern could extend to the other single-threshold decision points above.
- For genuinely borderline cases at any of these thresholds, lean on the pipeline's existing "prefer UNKNOWN over a forced wrong answer" principle more broadly — flag as uncertain/needs-review instead of a hard binary cutoff, rather than only applying that principle to cell-value extraction.

### Priority, if the user wants this addressed
